# New Item Creation / New Item Recheck — Specification

วันที่: 2026-10-01
ฐานข้อกำหนด: ผู้ใช้ยืนยัน Q1–Q24 และ test seams แล้ว
สถานะ: พร้อมแตกงาน; spec นี้ไม่ใช่คำสั่งให้ implement หรือสร้างข้อมูลจริงบน Aztek

## Problem Statement

เมื่อ Item Finder หาไอเทมจากเอกสารไม่พบ ผู้ใช้ยังไม่มี flow ใน Tools สำหรับสร้าง Item ใหม่ รับ Aztek Item ID และตรวจว่าข้อมูลที่บันทึกตรงกับเอกสารก่อนนำไปจัด Bundle การกรอกทีละรายการเสี่ยงผิด ItemKind, Option, Duration หรือคุณสมบัติอื่น การลองบันทึกใหม่หลังการเชื่อมต่อหลุดเสี่ยงสร้างซ้ำ และการยุบรายการซ้ำอาจทำแถวอ้างอิงหรือ Amount ของแต่ละ Bundle หาย

## Solution

เพิ่มหน้า “สร้าง/ตรวจ Item” สำหรับ CABAL PC TH/SEA และ CABAL M TH/SEA รับ Excel แบบเลือก Sheet พร้อมพรีวิว รวมทั้งรายการที่ Item Finder หาไม่พบ มีเทมเพลต Excel สำหรับ Item ใหม่โดยตรง ผู้ใช้แก้ร่าง เติมช่องขาด เลือกเฉพาะรายการ และยืนยันก่อนสร้างจริง

ค้นหา Item เดิมก่อนสร้าง ให้ผู้ใช้ตัดสินใจใช้ ID เดิมหรือสร้างใหม่ หลังบันทึกแต่ละ Item ให้อ่านข้อมูลจริงกลับทำ New Item Recheck เทียบ New Item Reference แสดงต้นฉบับ ค่าที่ส่ง และค่าจริงแยกกัน ผลไม่ผ่านหรือการสร้างยังยืนยันไม่ได้ให้หยุดคิวโดยไม่บันทึกซ้ำ ผลผ่านส่ง ID กลับ Item Finder และผู้ใช้เลือกส่งต่อ Bundle เอง เก็บคิวและ New Item History ในเครื่องสำหรับทำงานต่อโดยไม่เริ่มสร้างอัตโนมัติเมื่อเปิดโปรแกรม

## User Stories

1. ในฐานะผู้เตรียมข้อมูล ฉันต้องการสร้าง Item record ใหม่บน Aztek เพื่อได้ Aztek Item ID สำหรับจัด Bundle
2. ในฐานะผู้ใช้ CABAL PC TH ฉันต้องการนำเข้าและสร้าง Item ในเกมที่เลือก เพื่อไม่ส่งข้อมูลผิดเกม
3. ในฐานะผู้ใช้ CABAL PC SEA ฉันต้องการใช้ flow เดียวกัน เพื่อทำงานโดยไม่ต้องเปลี่ยนวิธีเตรียมข้อมูล
4. ในฐานะผู้ใช้ CABAL M TH/SEA ฉันต้องการ flow เดียวกับ PC แต่ใช้ประเภทที่เกมรองรับ เพื่อไม่กรอกตัวเลือกที่ไม่มีจริง
5. ในฐานะผู้ใช้ Excel ฉันต้องการเลือกและค้นหา Sheet ด้วยชื่อจริง เพื่อไม่ดึงข้อมูลจากแท็บอื่นโดยไม่ตั้งใจ
6. ในฐานะผู้เตรียมข้อมูล ฉันต้องการดาวน์โหลดเทมเพลตหนึ่ง Item ต่อแถว เพื่อกรอกข้อมูลใหม่ได้ตรงรูปแบบ
7. ในฐานะผู้ใช้เอกสารแผนเดิม ฉันต้องการนำเข้าเอกสารเดิมได้ เพื่อไม่ต้องคัดลอกข้อมูลทั้งหมดลงเทมเพลตใหม่
8. ในฐานะผู้ใช้ Item Finder ฉันต้องการส่งรายการไม่พบไปหน้า “สร้าง/ตรวจ Item” เพื่อทำงานต่อพร้อมแหล่งอ้างอิงเดิม
9. ในฐานะผู้ตรวจร่าง ฉันต้องการเห็นชื่อ เกม คุณสมบัติและแหล่งที่มาของแต่ละรายการ เพื่อทบทวนก่อนสร้าง
10. ในฐานะผู้ตรวจร่าง ฉันต้องการเลือกเฉพาะรายการที่จะสร้าง เพื่อไม่สร้างทุกแถวที่นำเข้า
11. ในฐานะผู้ตรวจร่าง ฉันต้องการเห็นจำนวนและเกมในคำยืนยัน เพื่อรู้ขอบเขตการบันทึกจริง
12. ในฐานะผู้ตรวจร่าง ฉันต้องการเห็นช่องที่ขาดหรืออ่านไม่ได้ เพื่อเติมให้ครบก่อนสร้าง
13. ในฐานะผู้ตรวจร่าง ฉันต้องการให้ค่า 0 ที่ระบุจริงคงอยู่ เพื่อไม่สับสนกับช่องว่าง
14. ในฐานะผู้ตรวจร่าง ฉันต้องการใช้ Display Name ของแถวเป็นชื่อเริ่มต้น เพื่อรักษาชื่อจากเอกสารโดยไม่ใช้ชื่อ Sheet แทน
15. ในฐานะผู้ตรวจร่าง ฉันต้องการแก้ชื่อเองโดยไม่มีการตัดคำหรือจำนวนท้ายชื่ออัตโนมัติ เพื่อควบคุมชื่อที่ส่งสร้าง
16. ในฐานะผู้ใช้ PC ฉันต้องการเลือก GENERAL หรือ CABALPC_PREMIUM ตามฟอร์มจริง เพื่อสร้างประเภทที่ตั้งใจ
17. ในฐานะผู้ใช้ M ฉันต้องการเห็น GENERAL ตามฟอร์มจริง เพื่อไม่เข้าใจผิดว่าเลือก Premium ได้
18. ในฐานะผู้ตรวจร่าง ฉันต้องการยืนยัน GENERAL และสถานะผูกมัดเมื่อเอกสารไม่ได้ระบุ เพื่อรู้ว่ากำลังใช้ค่าเริ่มต้นตามนโยบาย
19. ในฐานะผู้ตรวจร่าง ฉันต้องการกำหนดแลกเปลี่ยนได้ต่อ Item เพื่อไม่สับสนกับความหมายของคอลัมน์อื่น
20. ในฐานะผู้ตรวจร่าง ฉันต้องการเพิ่มคำอธิบายหรือรูปเองเป็นตัวเลือก เพื่อไม่ต้องมีรูปครบทุก Item และไม่ใช้ไฟล์จากหน้าอื่นโดยไม่ตั้งใจ
21. ในฐานะผู้ใช้ ฉันต้องการค้นหา Item เดิมก่อนสร้าง เพื่อเลือกใช้รายการที่มีอยู่แทนการสร้างซ้ำ
22. ในฐานะผู้ใช้ ฉันต้องการเห็นทุกตัวเลือกเมื่อสามค่าเดียวกันพบหลาย ID เพื่อไม่ให้ระบบเลือก ID แทนฉัน
23. ในฐานะผู้เตรียมหลาย Bundle ฉันต้องการสร้างหนึ่ง Item เมื่อค่าที่ใช้สร้างเหมือนกันทั้งหมด เพื่อใช้ ID เดียวกลับทุกแถวอ้างอิง
24. ในฐานะผู้เตรียมหลาย Bundle ฉันต้องการรักษา Amt และตำแหน่งของแต่ละแถว เพื่อไม่ทำจำนวนรางวัลหรือรายการใน Bundle หาย
25. ในฐานะผู้ตรวจข้อมูล ฉันต้องการเก็บต้นฉบับแยกจากร่าง เพื่อไม่ให้การแก้ร่างเปลี่ยนหลักฐาน
26. ในฐานะผู้ตรวจข้อมูล ฉันต้องการตรวจค่าที่เติมในช่องว่างพร้อมเห็นว่า “กรอกเอง” เพื่อให้รีเช็คได้แม้เอกสารเดิมไม่ครบ
27. ในฐานะผู้ตรวจข้อมูล ฉันต้องการเห็นว่าค่าที่เปลี่ยนจากต้นฉบับไม่ตรงเอกสาร เพื่อไม่ให้การแก้ร่างทำผลตรวจผ่านผิดความหมาย
28. ในฐานะผู้ใช้ ฉันต้องการอ่าน Item ที่บันทึกจริงกลับหลังสร้าง เพื่อไม่ถือว่าเพียงกรอกฟอร์มสำเร็จแปลว่าข้อมูลถูกต้อง
29. ในฐานะผู้ตรวจ ฉันต้องการตรวจเกม/Item ID ชื่อ ประเภท ItemKind Option Duration และ Tradeable เพื่อรับรองคุณสมบัติที่สำคัญ
30. ในฐานะผู้ตรวจ ฉันต้องการตรวจคำอธิบายที่ส่งสร้างและเห็นสถานะรูปแยก เพื่อรู้ขอบเขตที่ระบบตรวจจริง
31. ในฐานะผู้ใช้ ฉันต้องการให้คิวหยุดเมื่อไม่ตรงหรืออ่านไม่ได้ เพื่อทบทวนก่อนทำรายการต่อไป
32. ในฐานะผู้ใช้ ฉันต้องการแยก “สร้างสำเร็จ” จาก “รีเช็คผ่าน” เพื่อไม่ส่งต่อรายการที่ยังมีปัญหา
33. ในฐานะผู้ใช้ ฉันต้องการให้การหลุดหลังบันทึกเป็น Unconfirmed Item Creation เพื่อไม่ retry แล้วสร้างซ้ำ
34. ในฐานะผู้ใช้ ฉันต้องการตรวจซ้ำจาก Item ID โดยอ่านอย่างเดียว เพื่อแก้ปัญหาการตรวจโดยไม่บันทึกใหม่
35. ในฐานะผู้ใช้ ฉันต้องการตรวจผล ข้าม หรือทำรายการอื่นต่อหลังรับทราบปัญหา เพื่อทำงานต่อได้โดยไม่เปลี่ยนผลเดิมให้ผ่าน
36. ในฐานะผู้ใช้ ฉันต้องการผูกเกมกับแต่ละรายการเมื่อเข้าคิว เพื่อให้การสลับเกมในหน้าอื่นไม่เปลี่ยนรายการค้าง
37. ในฐานะผู้ใช้ ฉันต้องการกู้คิวและดู New Item History หลังเปิดโปรแกรมใหม่ เพื่อทำงานต่อโดยไม่มีการสร้างอัตโนมัติ
38. ในฐานะผู้ตรวจ ฉันต้องการดูผลตรวจแต่ละรอบพร้อมเวลา ต้นทาง ค่าที่ส่ง และค่าจริง เพื่อย้อนตรวจเหตุการณ์ได้
39. ในฐานะผู้ใช้ Item Finder ฉันต้องการรับเฉพาะ ID ที่ตรวจผ่าน เพื่อไม่ใช้ผลผิดหรือยังยืนยันไม่ได้
40. ในฐานะผู้เตรียม Bundle ฉันต้องการกดส่งเฉพาะผลผ่านที่เลือกเอง เพื่อไม่เพิ่มคิว Bundle อัตโนมัติหรือดึงรายการอื่นมาด้วย
41. ในฐานะผู้ใช้คีย์บอร์ดและจอเล็ก ฉันต้องการเลือก Sheet แก้ร่าง ยืนยัน และอ่านผลได้ เพื่อทำงานครบ flow โดยไม่ติดปุ่มหรือข้อมูลที่ล้นหน้าจอ
42. ในฐานะผู้ใช้ ฉันต้องการข้อความผิดพลาดที่บอกสถานะและสิ่งที่ทำต่อได้ เพื่อไม่เข้าใจผิดว่าต้องกดสร้างซ้ำ

## Implementation Decisions

### ขอบเขตและโครงสร้าง

- ใช้ New Item Creation, Aztek Item ID, New Item Recheck, New Item Reference, Unconfirmed Item Creation และ New Item History ตาม glossary เดิม ไม่เปลี่ยนความหมาย Document Reference ของ Bundle
- เพิ่มความสามารถเฉพาะการสร้าง/ตรวจ Item ในพื้นที่ทำงานเดิม ใช้ระบบเกม การเชื่อม Aztek ควบคุมงาน และการเก็บข้อมูลเดิม ไม่สร้าง framework automation หรือระบบคิวใหม่ทั้งชุด
- ส่วนที่ต้องเพิ่มหรือปรับมี importer/template, คิวและประวัติ Item, runner สร้าง/อ่านกลับ, การเปรียบเทียบ และจุด handoff ของ Item Finder ใช้ flow ธุรกิจร่วม ส่วนความต่างฟอร์มแยกตามเกม
- รองรับ PC TH/SEA และ M TH/SEA ไม่รวม HOF; PC มี GENERAL/CABALPC_PREMIUM ส่วน M แสดง GENERAL ตายตัว ตาม DOM ที่ตรวจเมื่อ 2026-10-01
- แต่ละรายการผูกเกมเมื่อเข้าคิว สร้างทีละเกม การสลับเกมในหน้าอื่นไม่แก้เกมของร่างหรือประวัติ

### นำเข้าและความพร้อม

- เทมเพลตหนึ่ง Item ต่อแถว มี Name, ItemKind, Option, Duration, Item Type, Tradeable และ Description; คำอธิบายไม่บังคับ เลือกเกมตอนนำเข้า
- Excel ใช้รูปแบบเลือก/ค้นหา Sheet และพรีวิวเดิม รับทั้งเทมเพลตใหม่กับเอกสารแผนเดิม; แสดงคำเตือน/ช่องขาดพร้อมต้นทาง ไม่เปลี่ยนไฟล์ที่อัปโหลด
- Item Finder ส่งรายการไม่พบพร้อมแหล่งอ้างอิงเดิม ผู้ใช้ตรวจและเลือกขอบเขตก่อนสร้าง; การนำเข้าหรือเปิดพรีวิวไม่มีผลบันทึก Aztek
- ชื่อเริ่มจาก Display Name ของแถว ไม่ใช้ชื่อ Sheet ไม่ตัดคำหรือจำนวนท้ายชื่ออัตโนมัติ ชื่อว่างต้องเติม
- ItemKind, Option และ Duration ที่ขาดหรืออ่านไม่ได้ต้องเติมและยืนยันก่อนสร้าง ไม่ใช้ placeholder ของ Aztek แทนข้อมูลจริง ไม่เดา 0; 0 ที่ระบุชัดเป็นค่าจริง
- Type ที่ต้นทางไม่มีเริ่ม GENERAL และ Tradeable ที่ไม่มีเริ่มผูกมัด/แลกเปลี่ยนไม่ได้ โดยระบุว่าเป็นค่าเริ่มต้นให้ยืนยัน ไม่เดา Premium จากชื่อ
- ค่าประเภทที่เกมไม่รองรับต้องแจ้งไม่พร้อม ไม่แปลงเป็น GENERAL เงียบ ๆ; คอลัมน์ Yes/No ที่ความหมายกำกวม เช่น Itemmove ไม่ map เป็น Tradeable เอง
- รูปและคำอธิบายกรอกเพิ่มเองเป็นตัวเลือก ไม่มีการดึงรูป Excel หรือใช้ไฟล์จากหน้าอื่นโดยปริยาย รุ่นแรกปิดแสดงบนเว็บและไม่รองรับพารามิเตอร์เว็บ
- Amt ไม่ใช่จำนวนครั้งที่สร้าง Item; เก็บ Amt แยกเพื่อส่งกลับแต่ละ occurrence ใน Bundle

### ข้อมูลอ้างอิง การรวมแถว และประวัติ

- เก็บต้นฉบับพร้อม filename/Sheet/row และทุก occurrence แยกจากร่าง ค่าที่ส่งสร้าง และข้อมูลจริงที่อ่านกลับ
- New Item Reference ใช้ค่าที่ต้นฉบับระบุ ส่วนช่องที่ต้นฉบับไม่มีใช้ค่าที่ผู้ใช้เติมหรือยืนยันค่าเริ่มต้น พร้อม provenance ต่อช่อง; รักษาต้นฉบับว่างไว้
- การเปลี่ยนค่าที่ต้นฉบับมีอยู่แล้วไม่เปลี่ยน reference ให้เท่าร่าง แม้ Aztek บันทึกตามร่างถูกต้องยังต้องแสดงไม่ตรงเอกสาร
- ก่อนเริ่มสร้างตรึงร่างที่ยืนยันและ reference สำหรับรอบนั้น ไม่ใช้ร่างล่าสุดที่เปลี่ยนภายหลังแทนค่าประวัติ
- รวมเป็นหนึ่งการสร้างได้เมื่อเกมและคุณสมบัติที่ใช้สร้างเหมือนกันทั้งหมด รวมชื่อ ประเภท Tradeable คำอธิบายและรูปถ้ามี; ห้ามรวมเพียงเพราะ ItemKind/Option/Duration เหมือนกันเมื่อค่าอื่นต่าง
- หนึ่ง Item ที่รวมแถวต้องรักษาความสัมพันธ์กลับทุกต้นทางและ Amt/ตำแหน่งแยกกัน; ผลผ่านหนึ่ง ID อาจใช้กับหลาย occurrence โดยไม่ยุบรายการ Bundle
- ผลต่างต่อ occurrence ยังต้องเห็นได้ การรวมแถวไม่ทำให้ต้นทางที่ไม่ตรงกลายเป็นผ่าน
- เก็บคิว เกม Item ID, reference ค่าที่ส่ง ผลสร้าง ผลตรวจ และประวัติแต่ละรอบในเครื่อง ใช้ที่เก็บเดิมโดยเพิ่มข้อมูลเท่าที่จำเป็น; ไม่บันทึก cookie/token/login secrets ลงประวัติ
- เปิดใหม่กู้ข้อมูลไว้ให้ตรวจและทำงานต่อ ไม่เริ่มบันทึกคิวค้างเอง หากหลักฐานเดิมชี้ว่าเริ่ม submit แล้ว ให้รักษาสถานะไม่แน่นอน ไม่ย้อนเป็นร่างที่สร้างได้ทันที

### ค้นก่อนสร้างและสัญญาการทำงาน

- ค้นก่อนสร้างด้วยเกม + ItemKind/Option/Duration ใช้ผลชื่อเพื่อประกอบการเปรียบเทียบ ไม่ใช้ชื่อเป็น identity
- หากพบ ให้แสดงรายการที่พบเทียบต้นทาง ผู้ใช้เลือกใช้ Aztek Item ID เดิมหรือยืนยันสร้างใหม่ ไม่มีการเลือก ID อัตโนมัติเมื่อพบหลายรายการ
- ID เดิมที่ผู้ใช้เลือกต้องอ่านกลับเทียบ reference ก่อนส่งต่อเช่นเดียวกับ Item ใหม่ ไม่ถือว่าผลค้นหาเก่าเป็นผลตรวจจริง
- จุดสั่งงานแยก import/preview, ยืนยันร่าง, สร้างรายการที่เลือก, ตรวจซ้ำ, อ่านคิว/ประวัติ และ handoff; ชื่อ route และ schema รายละเอียดกำหนดตาม convention เดิมในขั้นแตกงาน ไม่กำหนด framework ใหม่
- API ต้องบังคับขอบเขตรายการที่เลือก เกม ความพร้อมและสิทธิ์ใช้งานเดิมที่ฝั่ง server ไม่พึ่ง checkbox หรือปุ่ม disabled เพียงอย่างเดียว
- ปุ่มสร้างแสดงจำนวนและเกม พร้อมยืนยันก่อนบันทึกจริง การยกเลิกไม่ submit และไม่ทำข้อมูลร่างหาย
- ใช้กลไกควบคุมงานเดิมป้องกันการสั่งซ้ำ/ทับงานที่กำลังรัน ปุ่มตรวจซ้ำและ handoff ไม่เรียกคำสั่งสร้าง

### การอ่านกลับและผลตรวจ

- หลังบันทึกแต่ละ Item เก็บหลักฐานผลสร้างและ Aztek Item ID ก่อนเริ่มตรวจ อ่าน Item ที่บันทึกจริงใหม่ ไม่ใช้ค่าฟอร์มที่กรอกหรือผลค้นหาเก่าแทน actual
- ตรวจเกม/Item ID และคุณสมบัติชื่อ Type, ItemKind, Option, Duration, Tradeable รวมคำอธิบายเมื่อส่งสร้าง เทียบ reference และแสดงค่าที่ส่งสร้างประกอบ
- รายงานความต่างและความครบของข้อมูลรายช่อง ช่องหลักที่ต้องตรวจแต่ไม่มี reference หรืออ่านไม่ได้ไม่ถือว่าผ่าน
- รูปที่แนบรายงานสถานะว่ามีรูปแยกจากผลตรวจคุณสมบัติ ไม่อ้างว่าตรวจความเหมือนของเนื้อหา/พิกเซลแล้ว; รูปที่ไม่ได้แนบไม่เป็นข้อบังคับ
- ผลสร้างกับผลตรวจเป็นคนละสถานะ: สร้างสำเร็จยังไม่เท่ากับตรวจผ่าน และการรับทราบ/ทำต่อไม่เปลี่ยนผลตรวจ

| เหตุการณ์ | ผลและพฤติกรรมที่ต้องเห็น |
| --- | --- |
| ข้อมูลที่ต้องตรวจครบและตรง reference | ผ่าน; ทำ Item ถัดไปในชุดที่ยืนยัน และมีสิทธิ์ส่ง ID กลับ |
| มีค่าที่อ่านได้ต่าง reference | ไม่ตรง; แสดงความต่างและส่วนที่ตรวจไม่ครบถ้ามี หยุดคิว |
| ช่องหลักอ่านไม่ได้/การเชื่อมต่อมีปัญหา | ตรวจไม่สำเร็จหรือได้บางส่วนตาม coverage; หยุดคิว ไม่อ้างผ่าน |
| submit ไปแล้ว แต่ยังพิสูจน์ผลหรือ Item ID ไม่ได้ | Unconfirmed Item Creation; หยุดคิว ค้น/ตรวจหลักฐาน ห้าม auto-submit ซ้ำ |
| ผู้ใช้ตรวจซ้ำจาก ID ที่ระบุได้แน่นอน | อ่านอย่างเดียว เพิ่มผลรอบใหม่ ไม่สร้าง/แก้ Item |
| ผู้ใช้รับทราบแล้วข้าม/ทำรายการอื่นต่อ | คงผลปัญหาเดิมและสิทธิ์ส่งต่อเดิม ไม่เปลี่ยนเป็นผ่าน |

- session หมดอายุหรือ browser หลุดต้องแจ้งสิ่งที่ทำต่อได้ โดยรักษา checkpoint; ไม่รายงานว่าไม่สร้างแล้วเพียงเพราะคำตอบหาย
- การกู้ Unconfirmed Item Creation ต้องยืนยันเกมและตัวรายการจากหลักฐานที่เพียงพอ ไม่เลือกด้วยชื่อหรือสามค่าโดยลำพังเมื่อมีหลาย candidate
- ผลไม่ผ่าน/ยังยืนยันไม่ได้ไม่ส่งกลับเป็นผลพร้อมใช้และไม่ส่งต่อ Bundle ไม่มีทางรับทราบแล้ว bypass เป็นผลผ่าน
- ส่งผลผ่านกลับ Item Finder พร้อมทุกแถวอ้างอิง จากนั้นผู้ใช้กดส่งเฉพาะที่เลือกไป Bundle; ไม่เพิ่มคิว Bundle อัตโนมัติและไม่รวมแถวที่ไม่ได้เลือก

## Testing Decisions

แนวทดสอบได้รับการยืนยันจากผู้ใช้แล้ว: ใช้ API และ runner จริง จำลองเฉพาะขอบเขตเว็บ Aztek และตรวจ browser UI ด้วย Playwright ไม่มีการสร้างข้อมูลจริงบนระบบบริษัท

- ทดสอบพฤติกรรมภายนอกและผลที่ผู้ใช้เห็น: จำนวนการ submit, การหยุดคิว, ผลตรวจ, ข้อมูลที่คงอยู่และ handoff ไม่ผูกกับชื่อ helper ลำดับ method หรือจำนวน mock calls ภายใน
- ขอบเขตจำลองหลักคือ traffic ของ Aztek ที่ browser ใช้ ให้ runner ผ่านฟอร์ม/คำตอบจำลองจริงตามรูปแบบ API/runner integration ของ Bundle Recheck เดิม ห้าม fake ผล runner ให้ผ่านโดยไม่ทดสอบ checkpoint และการอ่านกลับ
- importer/template, คิว/ประวัติและการเปรียบเทียบตรวจผ่าน public API/ผลลัพธ์ที่บันทึกเท่าที่ทำได้ ใช้ seam เดิมของ import, Sheet picker และ finder-to-bundle handoff ไม่เพิ่ม seam แยกให้ทุก helper
- DOM fixtures ของฟอร์มสร้างต้องอ้างอิงหลักฐานจริงที่สำรวจไว้ ทั้ง PC select และ M GENERAL ตายตัว; DOM อ่านกลับคุณสมบัติอื่นต้องพิสูจน์และเพิ่ม fixture แยกก่อนอ้างว่ารองรับครบ
- ปิด network จริงในชุดทดสอบ synthetic ให้ request ที่ไม่ได้คาดไว้ล้มเหลว เพื่อไม่ส่ง traffic ไป Aztek จริงโดยหลุดจาก stub

### เกณฑ์ยอมรับหลัก

1. Import workbook หลาย Sheet แล้วเลือกบาง Sheet ได้ด้วยชื่อจริง แถวจาก Sheet ที่ไม่ได้เลือกไม่เข้าชุดสร้าง และไฟล์ต้นทางไม่เปลี่ยน
2. เทมเพลตดาวน์โหลดแล้วนำเข้ากลับได้ตามรูปแบบ ตัวอย่างที่ไม่ใช่ข้อมูลพร้อมสร้างไม่ทำให้เกิด Item จริงหรือการ submit
3. รายการไม่พบจาก Item Finder รักษา source และทุก occurrence; ไม่ดึงผลที่หาเจอทั้งหมดเข้าสร้าง
4. Option/Duration เป็น 0 ผ่านเมื่อระบุชัด ช่องว่างหรือค่าที่อ่านไม่ได้ไม่ถูกแปลงเป็น 0 และยังไม่พร้อมสร้าง
5. GENERAL/ผูกมัดที่ต้นทางไม่มีแสดง provenance และต้องยืนยัน; M ที่ระบุ Premium ไม่ถูกแปลงเงียบ ๆ
6. เติม Duration ที่ต้นฉบับไม่มีเป็น 9 แล้ว actual 9 ตรวจได้พร้อมแสดงกรอกเอง แต่ต้นฉบับ 9 แก้ส่งเป็น 0 และ actual 0 ต้องยังรายงานไม่ตรงเอกสาร
7. สร้างเฉพาะรายการที่เลือก ยกเลิกคำยืนยันมีจำนวน submit เป็น 0 และไม่ทำร่างหาย
8. สามค่าเดียวกันหลาย ID ไม่เลือก ID เอง การเลือกใช้ ID เดิมไม่ submit สร้างใหม่ แต่ต้องอ่าน actual ก่อนส่งต่อ
9. ค่าที่ใช้สร้างเหมือนกันทั้งหมดสร้างครั้งเดียวและคืน ID ทุก occurrence; ค่าอื่นต่างหรือเกมต่างไม่ถูกรวม
10. Item ซ้ำหลาย Bundle รักษา Amt และตำแหน่งแยกทุกแถว ไม่ใช้ Amt เป็นจำนวนครั้งสร้าง
11. actual ตรงทุกช่องหลักเป็นผ่าน; เปลี่ยนแต่ละคุณสมบัติหนึ่งช่องทำให้ไม่ตรง; missing actual ไม่ถูกตีความเป็น 0/false/ผ่าน
12. บันทึกรายการแรกแล้ว mismatch หรือ unreadable ต้องไม่ submit รายการถัดไปจนผู้ใช้ตัดสินใจทำต่อ
13. จำลองหลุดหลัง server รับ submit แต่ก่อนรับ ID ได้ Unconfirmed Item Creation; การกดซ้ำ/เปิดโปรแกรมใหม่ไม่เพิ่ม submit และไม่หายจากประวัติ
14. สร้างสำเร็จได้ ID แล้วตรวจไม่สำเร็จ ตรวจซ้ำเพิ่มประวัติและอ่านอย่างเดียว จำนวน submit ไม่เพิ่ม
15. รับทราบ/ข้ามไม่เปลี่ยนผลไม่ผ่าน และไม่เปิดทางส่งรายการนั้นเข้า Bundle
16. เปิดใหม่กู้เกม reference ค่าที่ส่ง Item ID และผลตรวจครบ ไม่สร้างคิวค้างอัตโนมัติ; ประวัติไม่เก็บ login secrets
17. สลับเกมในหน้าอื่นไม่เปลี่ยนเกมของคิวเดิม และ API ปฏิเสธชุดสร้างที่ผิดขอบเขต/ไม่พร้อม
18. ส่งเฉพาะผลผ่านที่เลือกกลับ Item Finder/Bundle ไม่ส่งผลอื่น ไม่ auto-add และรักษารายการซ้ำข้าม Bundle
19. กรณีมีรูปแสดงขอบเขตตรวจ presence แยก ไม่แสดงว่าพิสูจน์เนื้อหารูปตรงแล้ว กรณีไม่มีรูปไม่บังคับแนบ
20. Playwright ตรวจอย่างน้อย Desktop 1280×900 และ Mobile 390×844: import → เลือก Sheet → preview → เลือกรายการ → ยืนยัน → เห็นผล → ส่งเฉพาะที่เลือก พร้อม keyboard Tab/Space/Enter และ focus หลัง dialog
21. จอเล็ก ชื่อไทย/ชื่อยาว รายการมากและตารางผลมี scroll ที่ใช้งานได้ ไม่ตัด primary action หรือทำ horizontal overflow ทั้งหน้าโดยไม่มีพื้นที่เลื่อนที่ชัดเจน
22. Regression ของ Item Finder, Bundle Recheck และ handoff เดิมยังผ่าน; ไม่เปลี่ยนหลักฐานหรือสิทธิ์ส่งต่อของ Bundle โดยใช้กฎ New Item แทน

## Out of Scope

- การแก้หรือลบ Item เดิมบน Aztek อัตโนมัติ
- HOF และเกมนอก PC/M TH/SEA
- การสร้าง Bundle จากหน้านี้ทันทีหรือเพิ่มคิว Bundle อัตโนมัติ
- การ bypass ผลไม่ผ่านเพื่อส่งต่อ หรือ auto-submit ซ้ำหลังผลบันทึกไม่แน่นอน
- ดึงรูปจาก Excel อัตโนมัติ ใช้รูปจากหน้าอื่นเอง หรือพิสูจน์เนื้อหารูปตรงแบบพิกเซล
- เปิดแสดงบนเว็บและพารามิเตอร์เว็บเพิ่มเติม
- การสร้างข้อมูลจริงเพื่อทดสอบ โดยยังไม่มีคำสั่งผู้ใช้แยกต่างหาก
- Setup, commit, push, publish โปรแกรม และ deployment จากการทำ spec นี้
- framework automation ใหม่ การจัดระบบทั้งเว็บใหม่ หรือการรีแฟกเตอร์ที่ไม่จำเป็นกับ flow นี้

## Further Notes

- สรุปจากข้อยืนยัน Q1–Q24 และการยืนยัน test seams โดยไม่เพิ่มรอบสัมภาษณ์
- หลักฐานฟอร์มสร้างเมื่อ 2026-10-01 ครบสี่เกม: ชื่อ ItemKind, Option, Duration, คำอธิบาย, Tradeable, แสดงบนเว็บและรูปพบจริง; Option/Duration ว่างจริง ค่าใน placeholder ไม่ใช่ default
- DOM ไม่มี required/aria-required ที่ยืนยันกฎ server ได้ การสำรวจไม่ได้ submit จึงยังไม่พิสูจน์ validation, POST payload, การจับ ID หลังบันทึก หรือความครบของช่องอ่านกลับ
- ก่อน implement automation ต้องพิสูจน์ช่องอ่านกลับ/หลักฐานสำเร็จแบบ read-only เท่าที่ทำได้และใช้ fixture จากหลักฐานจริง หากช่องหลักยังอ่านไม่ได้ให้รายงานข้อจำกัด ไม่ลดเกณฑ์ผ่านเอง
- การทดสอบ save จริงบน Aztek ต้องรอการอนุมัติแยกและขอบเขตข้อมูลทดสอบที่ชัดเจน ชุด synthetic ไม่ใช่หลักฐานว่า server จริงรับค่าทุกแบบแล้ว
- การแตกงานถัดไปควรเรียง import/reference → create checkpoint/readback → recovery/history → handoff/UI verification โดยไม่ถือว่า spec ที่ ready-for-agent เป็นการเริ่ม implementation อัตโนมัติ
