# All for Cabal Update — อัปเดตผ่านโปรแกรมพร้อมรายละเอียดเวอร์ชัน

สถานะ: ดำเนินการตามคำสั่ง `implement` แล้วใน Local checkout; ยังไม่เผยแพร่ Release หรือ GitHub Issue ดูผลตรวจใน `docs/verification/2026-09-14-local-auto-update.md`

## Problem Statement

ผู้ใช้งาน All for Cabal ที่ติดตั้งโปรแกรมแล้วต้องไปดาวน์โหลด Setup ใหม่เองทุกครั้งที่ผู้ดูแลปล่อยเวอร์ชัน ทำให้บางคนใช้รุ่นเก่าและไม่ทราบว่ารุ่นใหม่แก้ไขหรือเพิ่มอะไร ผู้ดูแลต้องการปล่อย Release เหมือนเดิม แล้วให้แต่ละเครื่องอัปเดตจากในโปรแกรมได้โดยรักษาข้อมูลและงานที่เตรียมไว้

## Solution

เพิ่ม All for Cabal Update ให้โปรแกรมตรวจเวอร์ชันเมื่อเปิดใช้งาน หากมีรุ่นใหม่ให้แสดง Update Details Popup เป็นภาษาไทย ระบุเวอร์ชันปัจจุบัน เวอร์ชันใหม่ และรายการแก้ไข ผู้ใช้เลือกกดอัปเดตเองหรือปิด popup เพื่อใช้รุ่นเดิมต่อได้ มีปุ่มเปิดดูรายละเอียดซ้ำและปุ่มตรวจอัปเดตเองในหน้าเครื่องมือ

รุ่นแรกดาวน์โหลด Setup เต็มให้อัตโนมัติ ตรวจความครบของไฟล์ แล้วปิดโปรแกรมเพื่อติดตั้งและเปิดกลับ ผู้ใช้ไม่ต้องเปิด GitHub หรือเดินขั้นตอน Setup เองตามปกติ แต่ปริมาณดาวน์โหลดยังเท่ากับ Setup เต็ม ไม่ใช่แพตช์เฉพาะไฟล์ที่เปลี่ยน

ถ้ามีงานกำลังทำ ระบบให้รอจนงานเสร็จแล้วกดอัปเดตใหม่ เก็บร่างและคิวที่ยังไม่ได้สร้าง พร้อมเตือนเรื่องไฟล์หรือหน้า Aztek ที่ค้างก่อนปิดโปรแกรม หากตรวจหรือดาวน์โหลดไม่สำเร็จให้ใช้รุ่นเดิมต่อได้ หากติดตั้งล้มเหลวให้แสดงสาเหตุและวิธีลองใหม่โดยรักษาข้อมูลผู้ใช้

## User Stories

1. As an ผู้ใช้งานที่ติดตั้งโปรแกรมแล้ว, I want ตรวจเวอร์ชันใหม่ตอนเปิดโปรแกรม, so that ไม่ต้องติดตาม Release เอง
2. As an ผู้ใช้งาน, I want เห็นเวอร์ชันปัจจุบันและเวอร์ชันที่กำลังจะติดตั้ง, so that รู้ว่ากำลังเปลี่ยนเป็นรุ่นใด
3. As an ผู้ใช้งาน, I want เห็นรายการแก้ไขและสิ่งที่เพิ่มใน Update Details Popup, so that เข้าใจประโยชน์ของการอัปเดต
4. As an ผู้ใช้งาน, I want popup อัตโนมัติปรากฏครั้งเดียวต่อเวอร์ชันใหม่, so that การเปลี่ยนหน้าและเปิดโปรแกรมซ้ำไม่รบกวนงาน
5. As an ผู้ใช้งาน, I want มีปุ่มเปิดรายละเอียดซ้ำ, so that กลับมาอ่านหรืออัปเดตหลังปิด popup ได้
6. As an ผู้ใช้งาน, I want กดตรวจอัปเดตเองได้, so that รับรุ่นที่เพิ่งปล่อยโดยไม่ต้องปิดเปิดโปรแกรม
7. As an ผู้ใช้งาน, I want กดเริ่มอัปเดตด้วยตัวเอง, so that เลือกเวลาที่พร้อมหยุดใช้งานชั่วคราว
8. As an ผู้ใช้งาน, I want ปิด popup และใช้รุ่นเดิมต่อได้, so that งานประจำไม่ขึ้นกับการอัปเดตทันที
9. As an ผู้ใช้งานที่เชื่อมต่อไม่ได้, I want ได้รับข้อความเข้าใจง่ายและใช้รุ่นเดิมต่อได้, so that ปัญหาเครือข่ายไม่ทำให้โปรแกรมใช้ไม่ได้
10. As an ผู้ใช้งาน, I want โปรแกรมดาวน์โหลดและติดตั้ง Setup ให้, so that ไม่ต้องไปค้นหาไฟล์หรือติดตั้งด้วยตนเองตามปกติ
11. As an ผู้ใช้งาน, I want เห็นสถานะดาวน์โหลด ตรวจไฟล์ และติดตั้ง, so that รู้ว่าโปรแกรมกำลังทำอะไรและยังทำงานอยู่
12. As an ผู้ใช้งาน, I want ไฟล์ที่โหลดไม่ครบหรือ checksum ไม่ตรงถูกปฏิเสธ, so that ไม่ติดตั้งแพ็กเกจที่เสียหาย
13. As an ผู้ใช้งานที่กำลังค้นหาหรือสร้างข้อมูล, I want โปรแกรมปฏิเสธการติดตั้งขณะงานยังไม่เสร็จ, so that งานไม่ถูกตัดกลางทาง
14. As an ผู้ใช้งาน, I want เป็นคนกดอัปเดตใหม่หลังงานจบ, so that โปรแกรมไม่ปิดทันทีโดยไม่คาดคิดเมื่อคิวว่าง
15. As an ผู้ใช้งานหลายแท็บ, I want ทุกแท็บรับรู้ว่ากำลังเตรียมติดตั้ง, so that ไม่เริ่มงานใหม่หรือแก้ร่างระหว่างปิดโปรแกรม
16. As an ผู้ใช้งาน, I want ร่าง ข้อมูลที่แก้ และรายการในคิวกลับมาหลังอัปเดต, so that ทำงานต่อโดยไม่กรอกใหม่
17. As an ผู้ใช้งาน, I want รายการที่สร้างสำเร็จแล้วยังคงสถานะเดิม, so that อัปเดตแล้วไม่ส่งสร้างซ้ำ
18. As an ผู้ใช้งาน, I want ได้รับคำเตือนเมื่อมีไฟล์ที่เลือกค้างหรือรูปที่ยังอยู่เฉพาะในหน่วยความจำ, so that รู้ว่าต้องจัดการหรือเลือกใหม่ก่อนทำงานต่อ
19. As an ผู้ใช้งานที่มีหน้า Aztek กรอกค้าง, I want ได้รับคำเตือนก่อนปิดหน้าที่โปรแกรมดูแล, so that ไม่เสียข้อมูลที่ยังไม่ได้บันทึกโดยไม่รู้ตัว
20. As an ผู้ใช้งาน, I want ฐานข้อมูล การตั้งค่า และ session Aztek ที่บันทึกไว้ยังอยู่, so that อัปเดตแล้วกลับมาใช้งานต่อได้
21. As an ผู้ใช้งาน, I want โปรแกรมเปิดกลับหลังติดตั้งสำเร็จ, so that ไม่ต้องหาและเปิดโปรแกรมเอง
22. As an ผู้ใช้งาน, I want ข้อผิดพลาดที่บอกขั้นตอนถัดไปและปุ่มลองใหม่, so that แก้ปัญหาอัปเดตได้แม้หน้าเว็บหลักเปิดไม่ขึ้น
23. As an ผู้ใช้งาน, I want กดอัปเดตซ้ำหรือกดจากสองแท็บแล้วเกิดการติดตั้งเพียงครั้งเดียว, so that โปรแกรมไม่ทำงานขัดกัน
24. As an ผู้ดูแล Release, I want ใช้ GitHub Release และรายการแก้ไขที่เผยแพร่ไว้เป็นแหล่งอัปเดต, so that ไม่ต้องดูแลระบบแจกโปรแกรมแยกอีกชุด
25. As an ผู้ดูแล Release, I want เวอร์ชันใน Setup โปรแกรม และข้อมูล Release ตรงกัน, so that แต่ละเครื่องตรวจรุ่นใหม่ได้ถูกต้อง
26. As an ผู้ใช้งานเดิม, I want มีคำแนะนำว่าต้องลง Setup ที่มี updater อีกหนึ่งครั้ง, so that เข้าใจว่าจะเริ่มอัปเดตผ่านโปรแกรมได้ตั้งแต่รุ่นใด

## Implementation Decisions

### ขอบเขตและแหล่ง Release

- ข้อตกลง Q1–Q8 เป็นข้อกำหนดผลิตภัณฑ์ รายละเอียดด้านล่างเป็นแนวทางวิศวกรรมที่เสนอให้รองรับข้อตกลงเหล่านั้น
- รองรับโปรแกรม Windows Local ที่ติดตั้งด้วย Setup เดิม ใช้ GitHub Releases ของ `momozxmo/tool-cabal-local` เป็นแหล่งเวอร์ชัน รายละเอียด และแพ็กเกจ ส่วน issue tracker สำหรับสเปกคือ `momozxmo/all-for-cabal`
- เลือกเฉพาะ Release ที่เผยแพร่จริงและเป็นรุ่นเสถียร ไม่เลือก draft หรือ prerelease เปรียบเทียบเลขเวอร์ชันตามลำดับเชิงตัวเลข ไม่เปรียบเทียบข้อความ ไม่เสนอรุ่นเท่ากันหรือเก่ากว่ารุ่นที่ติดตั้ง
- เพิ่มเวอร์ชันจากแหล่งเดียวในขั้น build ให้ Setup และ runtime ใช้ร่วมกัน เปิดเผยเวอร์ชันผ่านสถานะ Local เพื่อยืนยันหลังเปิดโปรแกรมกลับ
- ใช้ Setup เต็มและ SHA-256 ที่สร้างจากขั้น Release เดิม ไม่สร้างบริการอัปเดตหรือฐานข้อมูลกลางใหม่

### หน้าเว็บและการแจ้งเตือน

- ใช้ UI ร่วมบนหน้าเครื่องมือ Item Finder, Bundle, Item Code, Event และ Product มี Update Details Popup และปุ่มเปิดซ้ำ ไม่มีหน้าประวัติแยก
- ตรวจเบื้องหลังหนึ่งครั้งเมื่อเปิด Local runtime โดยไม่ขวางการเริ่มใช้งาน การเปิดหลายแท็บไม่ควรทำให้เรียกตรวจ Release ซ้ำโดยไม่จำเป็น
- บันทึกเวอร์ชันที่แสดง popup ไปแล้วในข้อมูล Local ของผู้ใช้ Windows นั้น เพื่อไม่เด้งซ้ำเมื่อเปลี่ยนหน้า เปิดหลายแท็บ หรือเปิดโปรแกรมใหม่ การตรวจเองยังแสดงผลและเปิดรายละเอียดได้
- Popup แสดงรุ่นปัจจุบัน รุ่นใหม่ รายการแก้ไข และปุ่มอัปเดต/ไว้ก่อน แสดงข้อมูล Release เป็นข้อความหรือ Markdown ที่กรองแล้ว ไม่รัน HTML หรือสคริปต์จาก Release notes
- ถ้าไม่มีรุ่นใหม่ให้แจ้งเมื่อผู้ใช้ตรวจเอง ถ้าตรวจอัตโนมัติแล้วเครือข่ายผิดพลาดให้คงการใช้งานเดิมและแสดงสถานะที่เปิดดูหรือลองใหม่ได้
- แสดงความคืบหน้าที่วัดได้ เช่น bytes ระหว่างดาวน์โหลด ส่วนการติดตั้งที่ไม่มีเปอร์เซ็นต์จริงใช้ข้อความสถานะ ไม่สร้างเปอร์เซ็นต์หลอก

### การประสานงานอัปเดตและงานในคิว

- ให้ runtime เป็นเจ้าของสถานะอัปเดตเพียงแห่งเดียว และ UI ทุกแท็บอ่านสถานะร่วมกัน สถานะต้องแยกได้ว่าไม่มีอัปเดต/มีรุ่นใหม่/กำลังดาวน์โหลด/ไฟล์พร้อม/ติดตั้ง/สำเร็จ/ผิดพลาด
- ใช้จุดควบคุมงาน Browser เดิมเป็นฐาน เพิ่มการตรวจงานที่กำลังทำ งานรอทำ และการกั้นรับงานใหม่โดยไม่ให้มีช่องว่างระหว่างตรวจว่าว่างกับเริ่มปิดโปรแกรม ต้องครอบคลุมการค้นหา สร้าง preview และเชื่อม session รวมถึงคำสั่งสร้างทุกอันที่กำลังเดินคิว
- คิวร่างที่ผู้ใช้ยังไม่ได้กดรันไม่ใช่งานกำลังทำ ต้องเก็บไว้ได้โดยไม่ทำให้อัปเดตไม่ได้ตลอดเวลา
- ถ้ามีงานขณะกดอัปเดต ให้ตอบข้อความรอจนงานเสร็จ ไม่ตั้งคิวติดตั้งอัตโนมัติ หากมีงานใหม่ระหว่างดาวน์โหลดให้ตรวจซ้ำก่อนติดตั้งและรอผู้ใช้กดใหม่
- เมื่อเตรียมติดตั้ง ให้กันงานใหม่และประสานทุกแท็บเพื่อบันทึกร่าง เมื่อบันทึกไม่ได้หรือแท็บที่กำลังแก้ไขยังไม่ตอบรับ ให้หยุดก่อนปิดโปรแกรมและแจ้งให้จัดการ ไม่อ้างว่าบันทึกสำเร็จ
- คำสั่งอัปเดตซ้ำต้องไม่สร้างการดาวน์โหลด/ติดตั้งซ้อน ใช้กลไก instance เดียวของ Launcher เดิมร่วมกับสถานะอัปเดต

### การเก็บข้อมูลและการปิดโปรแกรม

- ใช้กลไกเก็บร่าง/workspace เดิมเป็นหลัก ครอบคลุมค่าที่ผู้ใช้แก้ รายการคิว ลำดับ และสถานะสร้างสำเร็จ ไม่เริ่มส่งงานไป Aztek เองหลังอัปเดต
- รักษา browser origin ของ Local เดิมเพื่อให้เข้าถึง browser storage ต่อได้ ไม่เปลี่ยนพอร์ตหรือ hostname เป็นทางแก้เมื่ออัปเดต
- รักษาข้อมูลผู้ใช้ที่แยกจากไฟล์โปรแกรม รวมถึงฐานข้อมูล config กุญแจเข้ารหัส และ session ที่บันทึกไว้ การรักษา session ไม่ได้ต่ออายุ session ที่ Aztek ทำให้หมดอายุเอง
- ไฟล์ที่เลือกแต่ยังไม่ Import รวมถึงรูป/ไฟล์แนบในหน่วยความจำที่ยังไม่เก็บถาวร ต้องเตือนอย่างเจาะจง ให้กลับไปจัดการหรือยอมรับว่าต้องเลือกใหม่ได้ ไม่แสดงว่าไฟล์ถูกเก็บแล้วเพียงเพราะชื่อไฟล์ยังอยู่
- แสดงคำเตือนก่อนปิด preview หรือหน้า Aztek ที่โปรแกรมดูแล การอัปเดตต้องไม่กดบันทึก/สร้างจริงให้ผู้ใช้ และไม่ปิด browser อื่นที่ไม่ใช่ของโปรแกรม
- ใช้การสำรองฐานข้อมูลก่อน migration เดิม ตรวจให้จบก่อนเริ่มใช้งานรุ่นใหม่ ไม่สร้างระบบย้อนเวอร์ชันโปรแกรมเพิ่มเติมในรุ่นนี้
- ปิด Local server และ process ที่เกี่ยวข้องอย่างสุภาพและยืนยันว่าหยุดจริง ถ้าหยุดไม่ได้ ให้เลิกขั้นตอนติดตั้งและแสดงข้อผิดพลาด ไม่ใช้การบังคับปิดงานแทนการตรวจว่าง

### ดาวน์โหลด ติดตั้ง และข้อผิดพลาด

- เพิ่มส่วนประสานอัปเดตที่มีหน้าที่ตรวจ Release ดาวน์โหลด ตรวจไฟล์ และส่งต่อให้ตัวช่วยติดตั้ง โดยแยกผลข้างเคียงด้านเครือข่าย/ติดตั้งผ่านขอบเขตขนาดเล็กเพื่อทดสอบได้
- แพ็กเกจต้องมาจาก Release ที่กำหนดผ่าน HTTPS เท่านั้น ไม่รับ URL คำสั่ง shell หรือที่อยู่ไฟล์ executable ตามอำเภอใจจากหน้าเว็บ ตรวจ redirect และแหล่งดาวน์โหลดให้เป็นส่วนของบริการ Release ที่อนุญาต
- คำสั่งที่เริ่มดาวน์โหลด/ติดตั้งต้องผ่านการยืนยัน Local session และการป้องกัน request ข้าม origin ตามระบบเดิม ปิดความสามารถติดตั้งในโหมดที่ไม่ใช่ Windows Local ที่รองรับ
- ดาวน์โหลดลงพื้นที่ชั่วคราวแยกก่อน ตรวจความครบและ SHA-256 ก่อนเรียก Setup หากไฟล์หาย โหลดขาด hash ไม่ตรง หรือข้อมูล Release ไม่ครบ ต้องไม่เรียกตัวติดตั้ง
- ตรวจ hash เพื่อความครบของไฟล์ ไม่อ้างว่าเป็นลายเซ็นยืนยันผู้เผยแพร่ ความน่าเชื่อถือยังอิงแหล่ง Release ที่ควบคุมไว้
- ตัวช่วยติดตั้งต้องทำงานต่อได้หลัง Launcher เดิมปิด รัน Setup แบบไม่ต้องเดิน wizard และเปิด Launcher กลับผ่านช่องทาง Local เดิม ห้ามรายงานสำเร็จจากการเริ่ม process เพียงอย่างเดียว
- ถือว่าสำเร็จเมื่อ Setup จบสำเร็จและ Local runtime รุ่นเป้าหมายเปิดพร้อมใช้งาน ถ้าติดตั้งได้แต่เปิดหน้าเว็บไม่สำเร็จ แยกข้อความออกจากกรณีติดตั้งล้มเหลว
- ถ้าล้มเหลวก่อนติดตั้ง โปรแกรมเดิมต้องยังใช้ได้และปลดการกั้นงาน หากติดตั้งบางส่วนไปแล้ว ไม่รับประกันว่ารุ่นเก่าจะยังเปิดได้ ต้องมีช่องทางรายงานสาเหตุ/ลองใหม่ผ่านตัวช่วยที่ไม่พึ่งหน้าเว็บหลัก พร้อมข้อมูล log ที่ไม่เปิดเผย secrets
- เก็บผลของความพยายามล่าสุดเพื่อให้หลังเปิดใหม่หรือถูกขัดจังหวะไม่ติดสถานะกำลังอัปเดตตลอดไป ตรวจสภาพจริงก่อนเสนอ retry และไม่รันไฟล์ชั่วคราวที่ยังไม่ผ่านการตรวจ

## Testing Decisions

สถานะของหัวข้อนี้: ข้อเสนอสำหรับผู้ใช้ตรวจตามขั้นตอน `to-spec` ก่อนเผยแพร่ issue

- ใช้การทดสอบพฤติกรรมที่สังเกตได้เป็นหลัก: สิ่งที่เห็นบนหน้าเว็บ ผลคำสั่ง Local การอนุญาต/ปฏิเสธติดตั้ง และข้อมูลที่ยังอยู่หลังเปิดกลับ ไม่ผูกกับชื่อฟังก์ชัน จำนวนการเรียก helper หรือข้อความโค้ดภายใน
- จุดทดสอบหลักหนึ่งชุดคือ workflow จาก UI/Local API ผ่านส่วนประสานอัปเดตจริง จำลองเฉพาะผลข้างเคียงที่ขอบระบบ เช่น Release server การดาวน์โหลด และการเรียก/จบ process ติดตั้ง โดยไม่จำลองตรรกะตรวจงานว่างหรือการเก็บร่างที่ต้องพิสูจน์
- ใช้แนวทางเดิมจากชุดทดสอบ Launcher ซึ่งแทน HTTP/process/clock ได้ ชุด runtime ที่ตรวจการเก็บ secrets และสำรอง/คืนฐานข้อมูล และ Playwright ที่ตรวจหลายแท็บกับการคืน workspace
- เพิ่มการทดสอบระดับต่ำเฉพาะจุดที่ integration พิสูจน์ได้ไม่ชัด เช่น ลำดับเวอร์ชัน กรณีแข่งกันระหว่างงานใหม่กับการติดตั้ง และการปฏิเสธแหล่ง executable ที่ไม่ถูกต้อง ไม่สร้างชั้นทดสอบใหม่ทุกโมดูล
- การทดสอบอัตโนมัติไม่เรียก Setup จริงบนเครื่องพัฒนา และไม่สร้างข้อมูลจริงใน Aztek ใช้ fake งานที่ควบคุมจังหวะจบได้

### เงื่อนไขตรวจรับ

1. พบรุ่นเสถียรที่ใหม่กว่าแล้วแสดงรุ่น/รายละเอียดถูกต้อง ไม่เสนอรุ่นเดิม รุ่นเก่า draft หรือ prerelease รวมถึงกรณีเลขรุ่นเช่น 0.1.9 และ 0.1.30
2. Popup อัตโนมัติแสดงครั้งเดียวต่อรุ่นข้ามหน้า แท็บ และการเปิด runtime ใหม่ ปุ่มดูซ้ำและตรวจเองยังทำงาน
3. ปิด popup ไม่เริ่มดาวน์โหลด/ติดตั้ง ไม่มีรุ่นใหม่หรือเน็ตหลุดไม่ขวางการใช้โปรแกรมเดิม
4. Release notes ที่มี HTML อันตรายไม่รันสคริปต์ คำสั่งอัปเดตจาก session/origin ที่ไม่ถูกต้องถูกปฏิเสธ
5. เลือกอัปเดตแล้วเห็นความคืบหน้าตามจริง โหลดสำเร็จและ hash ตรงจึงส่งไปติดตั้ง ไฟล์ขาด/hash ผิด/แหล่งผิด/ข้อมูลขาดไม่เรียก Setup
6. งาน search/create/preview/session capture ที่ยังไม่จบ รวมถึงการรันทั้งคิว กั้นการติดตั้งได้ เมื่อจบแล้วไม่มีการติดตั้งเอง ต้องกดใหม่
7. กรณีงานเริ่มพร้อมคำสั่งติดตั้งต้องได้ลำดับที่ปลอดภัย: งานเริ่มแล้วอัปเดตถูกกั้น หรืออัปเดตจองขั้นปิดแล้วงานถูกปฏิเสธ ไม่เกิดทั้งสองอย่างพร้อมกัน
8. กดซ้ำหรือกดพร้อมกันจากสองแท็บเกิดการติดตั้งครั้งเดียว สถานะที่แสดงสอดคล้องกัน
9. ร่างและคิวจากทุกหน้าเครื่องมือ รวมค่าที่แก้เองและสถานะสร้างสำเร็จ กลับมาเหมือนเดิมหลังเปิดใหม่ ไม่มีการส่งสร้างซ้ำอัตโนมัติ
10. การเก็บร่างล้มเหลวหรือแท็บที่แก้ไขยังไม่พร้อมต้องไม่ปิดโปรแกรม ไฟล์ในหน่วยความจำและหน้า Aztek ค้างแสดงคำเตือนที่ดำเนินการต่อหรือกลับไปจัดการได้
11. ฐานข้อมูล config และ session ที่เก็บไว้ยังอ่านได้หลังอัปเดต ทดสอบด้วยข้อมูลจำลองและไม่ส่ง secrets เข้า log
12. ปิด server ไม่สำเร็จต้องไม่เริ่ม Setup; Setup ล้มเหลวแสดงสาเหตุและลองใหม่ได้แม้เว็บหลักไม่ทำงาน
13. Setup exit สำเร็จแต่ runtime ไม่พร้อมหรือเป็นคนละรุ่นต้องไม่รายงานอัปเดตสำเร็จทั้งหมด
14. เปิดหลังดาวน์โหลด/ติดตั้งถูกขัดจังหวะแล้วสถานะไม่ค้างและไม่ติดตั้งจากไฟล์ที่ยังไม่ผ่านการตรวจ
15. โหมดที่ไม่รองรับต้องไม่เปิดคำสั่งติดตั้ง แม้เรียก endpoint โดยตรง

### ตรวจติดตั้งจริงบน Windows

ก่อนปล่อยรุ่นที่มี updater ให้ทดสอบบนสภาพแวดล้อม Windows สำหรับทดสอบ: ติดตั้งรุ่นที่รองรับ updater จากนั้นอัปเกรดเป็นรุ่นทดสอบที่ใหม่กว่าด้วย Setup จริง ตรวจการปิด/เปิด process เวอร์ชันเป้าหมาย ข้อมูลจำลอง ร่าง/คิว และการลองใหม่หลังจำลองความผิดพลาด ไม่ใช้เครื่องผลิตหรือ session Aztek จริงเป็นข้อมูลทดสอบ

## Out of Scope

- แพตช์เฉพาะไฟล์ที่เปลี่ยนหรือ binary delta
- บังคับอัปเดต ติดตั้งเองทันที หรือติดตั้งอัตโนมัติทันทีที่คิวจบ
- ย้อนเวอร์ชันโปรแกรม/ฐานข้อมูลอัตโนมัติหลังอัปเดตล้มเหลว
- หน้าประวัติ Release แยก ระบบแอดมินอัปเดตเครื่องอื่น หรือการติดตามเวอร์ชันของสมาชิกทุกเครื่องจากส่วนกลาง
- การเปลี่ยนระบบ deploy เป็น Cloud หรือรองรับระบบปฏิบัติการใหม่
- การย้ายข้อมูลผู้ใช้ไป server กลาง การสำรอง browser ทั้งโปรไฟล์ หรือการเก็บไฟล์ที่ยังไม่ Import ทุกไฟล์ถาวร
- การแก้ข้อมูลหรือกดสร้างจริงใน Aztek ระหว่างอัปเดต
- การจัดหาหรือติดตั้งใบรับรอง code signing ใหม่ในงานนี้

## Further Notes

- ข้อตกลงผลิตภัณฑ์มาจากคำตอบ Q1–Q8 ของผู้ใช้ ไม่ต้องสัมภาษณ์ซ้ำก่อนทำสเปก
- ผู้ใช้ปัจจุบันต้องติดตั้ง Setup รุ่นที่เพิ่ม updater อีกหนึ่งครั้งก่อนใช้อัปเดตในโปรแกรมได้ รุ่นเก่าที่ไม่มี updater ไม่สามารถรับความสามารถนี้เอง
- session ที่บันทึกไว้จะถูกรักษา แต่ session หมดอายุจากฝั่ง Aztek ยังต้องเชื่อมใหม่ตามปกติ
- การดาวน์โหลดพลาดกับการติดตั้งพลาดเป็นคนละกรณี: ก่อนเริ่มติดตั้งยังใช้โปรแกรมเดิมได้ หลังแทนที่ไฟล์บางส่วนอาจต้องติดตั้งซ้ำเพื่อซ่อม รุ่นแรกไม่รับประกันการย้อนกลับ
- การทดสอบสร้างเฉพาะ Setup แยกสำหรับตรวจ updater ไม่ใช่ Release แจกทีม การเผยแพร่โปรแกรมยังต้องสั่งแยก
